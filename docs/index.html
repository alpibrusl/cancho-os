An operating system written in cancho, with no Linux and no C.

A kernel for the Raspberry Pi: the firmware loads one image, a page of assembly calls main, and everything after that is cancho, drivers included.

The question it exists to answer: can the compiler say, before the kernel runs, every address and every processor register it is able to touch, and which function holds which device?

Why an operating system, and why cancho

The first job is small and concrete: the safety controller of a robot arm (cancho-robot). A controller like that is only worth trusting if nothing under it can go around it.

Hardware is a capability

A device register is reached through an Mmio value whose type names the addresses it covers. A function that was lent the console cannot write to the servo bus: it is a type error.

Nothing underneath

No Linux, no libc, no C. What is not cancho is one page of assembly that boots and catches faults, and it exports nothing the kernel can call.

No code behind its back

Interrupts stay masked and are polled after wfi; a fault re-enters main, which reports it. So there is no handler running between two statements.

Checked in CI

Every change boots in QEMU with a scripted shell session, and the list of what the kernel can touch is a file in the repository that CI compares.

What it does today

Booted on a real Raspberry Pi 4 on 2026-11-26 (console, timer, MMU, fault report). The rest in QEMU: as a Pi 3 and a Pi 4 from one image, and on QEMU's own virt board for the network card.

Built

  • A serial console and a small shell
  • The timer and the interrupt controller, polled
  • The MMU: code read-only, data not executable, address 0 unmapped
  • A fault report that names the fault and the three registers
  • The Feetech servo bus, read only: servo scan, servo pos
  • The SO-101 arm's pose from its servos, and a safety check that judges a motion and sends nothing
  • A first network: ping, a UDP echo and a TCP echo answered, over a serial line and over Ethernet (a virtual card in QEMU); the kernel can ping and fetch a web page too
  • An address from the network (DHCP), a gateway, and names (DNS): http example.com 80 works
  • Random numbers from the board's generator (QEMU's and the Pi 3's), used to begin each connection
  • The shell over a TCP connection, off until the console turns it on (no password, no encryption: a step towards SSH)

Not built

  • Moving a servo (waits for the safety core's actuation side)
  • Separate programs, an SD card driver, files
  • Preemption, and more than one core
  • The Pi 5, which is the robot's board: its console, timer and memory map are written from the board's own device tree and have never run
  • SSH, a real network card, USB, display

What the kernel can touch, from the compiler

cancho authority reads the program and prints this. It is not a comment someone keeps up to date: a register that is not on the list cannot be reached, and the build fails if the list changes without the file changing.

The full report is docs/authority.txt. The language features behind it are in cancho: Mmio and Cpu.

Put it on a Pi 4

Nobody has done this yet. Everything above was measured in QEMU. These are the steps that should boot it on a board; if you run them, what the console prints is worth an issue.

You need a Raspberry Pi 4, a microSD card and a USB-serial cable with 3.3 V levels. A 5 V cable damages the pins.

1. Build the image

The compiler is built from cancho's main with clang alone; then the kernel. LLVM's ld.lld and llvm-objcopy must be on the path.

git clone https://github.com/alpibrusl/cancho && cd cancho
sh scripts/build-standalone.sh --out /tmp/cancho-out --rev $(git rev-parse HEAD)
cd .. && git clone https://github.com/alpibrusl/cancho-os && cd cancho-os
CANCHO=/tmp/cancho-out/cancho ./build.sh        # writes build/kernel8.img

2. Put the firmware on the card

The Pi's own firmware loads the kernel and is not part of this repository. Flash Raspberry Pi OS Lite with Raspberry Pi Imager, which leaves the firmware on the card's FAT partition (bootfs); or format the card FAT32 and copy start4.elf and fixup4.dat from raspberrypi/firmware.

3. Copy two files

The kernel and a four-line config.txt: 64-bit, this kernel, the UART on, and the PL011 on the header pins instead of the Bluetooth chip.

cp build/kernel8.img board/config.txt /Volumes/bootfs/     # macOS, card mounted as bootfs
diskutil eject /Volumes/bootfs

4. Wire the cable

On the 40-pin header: GND to pin 6, the cable's RX to pin 8 (GPIO14), the cable's TX to pin 10 (GPIO15). Leave the cable's power wire unconnected.

5. Open the console, then power the Pi

115200 baud, 8N1. It should print the banner, and about should say (Raspberry Pi 4).

screen /dev/cu.usbserial-XXXX 115200      # macOS; the name depends on the cable
picocom -b 115200 /dev/ttyUSB0            # Linux

Where a real board may differ from QEMU

  • The data cacheThe kernel turns it on with the MMU and does not invalidate it first. QEMU has no cache. A hang right after boot points here.
  • The UART clockThe divisor is for 48 MHz, the Pi 4's default. Garbage on the console points here.
  • The servo busIt does not work on a Pi 4 header yet: it is the mini UART, whose only header pins are the two the console uses. It has to move to another UART before a real arm can be read.

To try it without a board: ./run.sh boots the same image in QEMU (qemu-system-aarch64, version 9 or later for the Pi 4 model).

Status

  • Research. One kernel image that boots, reads and reports. It does not load programs yet, so it is not an operating system in the sense most people mean.
  • Measured in QEMU only, as a Pi 3 and a Pi 4. No real board has run it.
  • It cannot move a servo, by design, until the safety core's actuation side exists in cancho-robot.
  • What is next and why is in the roadmap.
